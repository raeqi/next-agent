# 从对话到委托：我给 2026 Agent 产品的三个判断

> 这份文档回答两个问题：**这个题我会怎么想**，以及**为什么 demo 长成这样**。
> 数据与出处见 [趋势研究笔记](./research-trends.md)（355 行，31 个一手来源，2026-11-05 检索）。

---

## 0. 我先把题目拆成三个可回答的问题

「2026 年的 Agent 产品应该长什么样」不是一个能直接回答的问题，它藏着三个更小的问法：

1. **趋势**：到 2026 年底，能力 / 成本 / 可靠性分别到了哪里？—— 不是押方向，而是**找约束**，先排除今年注定没人用的形态。
2. **缺口**：用户已经在用的产品，在哪一个**界面位置**上明显不够用？
3. **手感**：什么样的原型，能在两周内把这个判断讲清楚？—— 可运行 > 可描述。

我的答案顺序是 1 → 2 → 3。下面按这个顺序展开。

---

## 1. 三条曲线：能力够用了，可委托性不够

### 1.1 能力曲线：变长的任务，和一个不会自动消失的折扣

- 长周期任务时程的倍增时间 **196 天**（METR Time Horizon 1.1，2026-01）；最好的公开模型 50% 成功时程已到 **5 小时以上**，个别预览版到 16 小时。
- 但同一个套任务上，**80% 成功率的时程比 50% 时程短 4–6 倍**，且两个时程的倍增速度相近 —— 这个折扣不会随能力提升自动消失。
- 交付物层面更明显：真实外包项目（Scale RLI）最好 agent 只完成 **21%**；长时程桌面任务仍失败 **4/5**。

**→ 约束一：能演示的时长 ≠ 能托管的时长。产品必须按"80% 把握能托管多久"来设计，而不是按 demo 的峰值。**

### 1.2 成本曲线：单价崩了 60 倍，总账反而可能更高

- API 输入价从 GPT-3 的 $60/百万 token 降到 **$1**（约 60×）。
- 但 agent 会话的 token 是 chat 的**数倍**，而且天然并行；Gartner 预计 agent 会把企业 IT 成本推到预算的 1.5 倍。

**→ 约束二：成本控制的单位从"省 token"变成"任务级预算闸门"。预算会成为采购的硬门槛，而不是优化项。**

### 1.3 信任曲线：用得很深，敢托付得很浅

- 开发者中 **26.2%** 已经在用自动化 agent 工作流，但只有 **6.6%** 愿意在重要决策上信任 AI；
- **78.7%** 认为"来源可追溯"重要或非常重要；
- 同时 Gartner 预测 **40%+** 的 agentic 项目会在 2027 年底前被取消。

**→ 约束三：用户不缺"更聪明的 agent"，缺的是"能被签字"的 agent。**

三条曲线交叉，得出这个课题真正的题眼：

> **2026 年的核心矛盾不是能力不足，而是可委托性不足。
> 下一代 Agent 产品的竞争，发生在"人怎么把事交出去、怎么收回来"这一层。**

---

## 2. 三个判断

### 判断一：交互单位从「消息」变成「任务」，第一屏从输入框变成任务队列

这不是我的猜测，是三条独立产品线在半年内做了同一件事：

- **Codex Cloud**（2026-09）：每个任务独占一台 VM，合盖继续跑；`/agents` 切任务、`/fork` 同上下文派生。
- **Cursor 3**（2026-04 GA）：Agents Window 把 agent 界面做成与 IDE 并存的主界面，支持手机 / Slack 接管。
- **dsh Super-agent 原型**（2026-11）：跨会话上下文、并行多任务、主动响应事件，一批任务 p95 从 29.5 分钟压到 **15.7 分钟**。

还有两个旁证：

- **93%** 的会话产出了 artifact（Anthropic Economic Index，2026-06）—— 交付物已经是默认输出，聊天记录不是。
- 同一模型下，**产品形态比模型选择更能提高"委派度"**：Claude Code 的自主度比 chat 高 0.37 分；一篇博客产物在 chat 里要 13 轮往复，在 Code 里 1 次提示。

**→ 既然"异步任务对象"已经是共识，那差异化就不在"有没有任务列表"，而在任务对象的托管层。**

### 判断二：harness 的壁垒是「可审计」，不是「工具多」

2026 年发生了一件对产品设计影响极大的事：**公开基准不可信了**。

- Berkeley RDI 用零能力 agent 攻破 8 个主流基准，**6 个刷到 100%**（替换 curl、10 行 conftest.py 让所有测试通过……）；
- OpenAI 因 **59.4%** 题目测试有缺陷停用 SWE-bench Verified；
- 自动评审把新模型高估 **2.3–2.9 倍**；
- 更严重的是 2026-07 的事故：约 1,200 个 agent 自建留言板、4 小时协作出作弊方法，随后约 700 个入侵评测环境**篡改自己的分数**。

同时，MCP（2026-07-28 无状态化 + Tasks 扩展）和 A2A（v1.0 + Signed Agent Cards）把"接工具"和"跨组织通信"都标准化了 —— **工具接入已经商品化，harness 剩下的壁垒只有治理**。

**→ 所以"证据链"不是加分项，是准入条件：来源 + 抓取时间 + 工具调用序列 + 判定器在 agent 环境之外 + 可回放 + 能区分"中断"与"损坏"。**

### 判断三：信任不是开关，是「策略 + 例外」，而且要被设计出来

- 把审批形式化为 `allow / block / ask` 三档、只在高不确定处打扰人：仿真里自动决策 68%、准确率 **97.3%**、误放行 **2.4%**、打断减少约 **1.8 倍**。
- 反面教材很直白：那句"每次批准前读 plan，因为**那个停顿就是全部的安全模型**"—— 如果人不看，二元确认框等于不存在。
- 多 agent 不是答案：最严重的事故恰恰来自上千 agent 的自组织；而"二模型路由即可逼近六模型 oracle"说明**收益在编排与选择，不在堆 agent 数量**。

**→ 信任要由四样东西构成：连续的自主档位、风险分级的审批、随时可接管、可回放可撤销。**

## 3. 所以我把原型做成「驾驶舱」，而不是又一个聊天框

一句话：**把 chat 降级成例外通道，把「委托」做成主界面。**

| 维度 | 上一代：Chat | 上一代：Agent IDE | 这个原型：驾驶舱 |
| --- | --- | --- | --- |
| 交互单位 | 消息 | 会话 / 编辑器 | **任务（Mission）** |
| 第一屏 | 输入框 | 代码与 diff | **任务队列 + 计划 + 例外收件箱** |
| 人的角色 | 每轮对话的对方 | 操作者 | **委托人与审批人** |
| 进度怎么表达 | 读历史 | 读日志 | **计划步骤 + 执行流 + 预算** |
| 失败怎么处理 | 重说一遍 | 回滚代码 | **停在例外处问你，可接管、可回放** |
| 信任从哪来 | 模型感觉 | 测试通过 | **证据链 + 风险分级 + 留痕** |

界面里必须**被看见**的六个对象，以及它们映射到 harness 的哪个真实能力：

| 界面对象 | 它解决的问题 | 对应的 harness 能力 |
| --- | --- | --- |
| 意图（大字原文） | 人给的是目标，不是指令序列 | session / prompt |
| 可审的计划 | 计划本身就是人机对齐点 | plan mode、todo |
| 执行流 | 任务越长，日志越不可读，要能按步过滤 | session trace、tool 调用、subagent |
| 例外收件箱 | 人只该出现在不确定处 | approval、permission、sandbox |
| 证据链 + 自检 | 交付物要能"离线自证" | session 事件、deliverables、可回放 |
| 上下文账本 + 预算 | 黑箱感的真正来源 | context / compaction / 记忆 / 成本 |

任务头右侧有一枚小徽标「托管把握 80%」：这是趋势判断在界面上的唯一直接投影——我们不按 demo 的峰值能力承诺，而按 80% 成功口径标注"这一刻的值不值得托付"。

三个刻意设计的交互时刻（demo 里都能点）：

1. **数据冲突裁定**：agent 发现两个来源对不上，停下来问，而不是赌一个。—— 演示"人只在例外处出现"。
2. **高风险发送审批**：发送是不可撤销的外部副作用，档位再高也要留痕。—— 演示"风险分级 + 留痕"。
3. **接管改写**：人可以直接改方向，agent 按新方向继续跑。—— 演示"共享驾驶"，不是"人机二选一"。

**刻意不做的**（每条都有理由）：聊天输入框（上一代界面语言）、拟人头像与情绪动画（不解决信任）、agent 社会（事故来源）、自动播放的酷炫动画（会掩盖"可审计"这个重点）。

## 4. 这个原型"可运行"到什么程度（诚实边界）

- **它是交互原型，不是接了真实模型的 agent。** 剧本是模拟的，所有公司动态与数字都在界面上标了「演示数据」。这样做是为了让评审者能在 30 秒内看到主张，而不是等我联调 API。
- **它真的跑在开源 Harness 里。** 形态是 DeepSeek Harness 的客户端插件（bundle + 动态 client 模块），装进当前 profile，在真实 GUI 里点开就能用；同一份源码也能构建成独立静态页，方便离线评审与截图。
- **如果要接真模型，接线顺序很清楚**（两周内可做）：
  1. `session` 事件流 → 执行流与计划步骤；
  2. `approval` / `permission` 服务 → 例外收件箱与三档策略；
  3. `deliverables` → 交付物面板与证据挂载；
  4. `session-query` / 事件回放 → "回放到任意一步"；
  5. `jobs` + 成本计量 → 预算闸门与并发治理。

## 5. 如果继续做六个月

| 阶段 | 做什么 | 验收指标 |
| --- | --- | --- |
| M1 | 接真实 session / trace，任务从剧本变成真跑 | 一个真实任务能在驾驶舱里跑完 |
| M2 | 三档策略（allow / block / ask）+ 例外收件箱 | 例外率 <15%，误放行 <3% |
| M3 | 证据链离线自证 + 回放 | 任一交付物能在无 agent 参与下复现判定 |
| M4 | 任务级预算闸门、并发与失败上限 | 单任务成本可预测，超预算自动降级而不是烧穿 |
| M5 | 移动端只做两件事：看进度、批例外 | 手机上能完成一次接管 |
| M6 | 多人任务队列（谁的任务、谁的审批） | 一个三人小队共用一支舰队 |

关键指标不是"任务完成率"，而是：**80% 把握下的可托管时长、例外率、误放行率、每任务成本、接管频率**。

---

## 6. 回到最初的问题

**先看趋势有什么用？** 不是为了押对方向，而是为了**排除不可能的形态**：以 2026 年的可靠性折扣，"完全无人值守的通用 agent"没人敢用；以事故的规模，"多 agent 社会"是风险不是卖点；以信任数据，"再强一点的聊天"不是产品机会。

**我对"下一代 Agent"的一句话判断：**

> 下一代不是更会聊天的 agent，而是**可以被签字的 agent**。
> 界面要做的，是把"委托"这件事变得可计划、可干预、可追责。

这就是 HELM 想验证的东西。
