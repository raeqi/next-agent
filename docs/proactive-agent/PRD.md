# 拾遗：通用桌面个人助手

版本 v0.5 · 2026-11-11。本文同时描述产品目标、体验要求与当前实现边界；目标能力不代表已经上线。历史方案见 [v0.1 归档](archive/PRD-v0.1.md)，实现细节见 [架构说明](ARCHITECTURE.md)，研究依据与局限见 [趋势研究](../research-trends.md)。

## 产品定位

**拾遗是一个不用开口，也能主动干活的个人 Agent。**

核心触发来自电脑屏幕的变化：在用户授权范围内感知当前工作，理解上下文，主动判断是否需要介入，不要求用户先发指令或反复解释背景。能在授权范围内提前准备的先做；需要取舍或扩大权限时，带着具体方案找用户决定。

「不用开口」指不必主动提出任务，不指语音输入能力；「主动干活」是产品目标，不能据此声称当前已具备任意应用的全自动多步操作。观察、判断、准备与执行是连续流程，但各自有权限边界。当前已验证与未完成能力仍以下文为准。

拾遗作为原生桌宠常驻桌面，在用户授权的应用中观察页面变化，主动发现帮助机会；用户也可以直接委派任务。聊天承诺追踪是专项能力，不是产品边界。应用无需先适配聊天版式才可被发现。

## 为什么做它

个人 Agent 的价值不只在于接到任务后更能干，也在于减少用户发现、解释、监督与重复交代任务的负担。用户经常没有想到可以委派什么，或不愿为了一个小动作重新组织背景。

拾遗希望以持续、可控的工作上下文连接「发现机会」与「完成任务」：观察只是入口，建议要具体，执行要有结果，反馈能成为下一次工作的标准。桌宠提供一个持续存在、随时可关的轻量入口。

研究文档讨论了长时程任务、工具调用、常驻 Agent、审批边界、采用与弃用等趋势。它们是产品假设的背景，不是需求已被验证的证据；需要结合真实使用检验价值、成本与打扰程度。

## 目标用户与需求

首批面向在多个桌面应用间处理大量信息的知识工作者，如产品经理、研究人员、运营和开发者。共同需求包括：

- 不想反复复制背景，希望助手理解当前允许观察的内容。
- 遇到复杂资料、报错、表单或重复操作时，可以及时获得具体帮助。
- 可以主动委派分析、整理、计算和执行任务，离开界面后仍能查看进度与交付。
- 对观察范围、外部发送、原件修改和自动操作保留决定权。
- 希望纠正和偏好被记住，而不是每次重新交代。

## 产品原则

1. **先带来具体价值。** 能准备结果时带着结果来；还不确定需求时说明能帮什么。停留询问是轻量入口，不推断用户一定遇到困难。
2. **打扰有成本。** 建议有依据、能忽略、有冷却；停止帮助后不反复追问同一件事。
3. **观察与操作分别授权。** 允许看到不意味着允许修改或发送，应用白名单由实际发现驱动。
4. **结果可检查。** 明确处理对象、输入范围、工具步骤、交付与验证方式；失败和缺信息如实说明。
5. **保护原件。** 默认先生成影子产物；目标中的原件修改需要可审阅的变更、确认与恢复路径。
6. **反馈沉淀为可编辑规则。** 可复用偏好由用户确认后记录，有适用范围，可停用或删除。
7. **任务不被应用类型限制。** 专项适配提高理解质量，不决定能否观察一个应用；主动建议和直接委派应共用执行能力。

## 目标场景

以下是需要逐步验证的产品场景，并非全部已实现。

| 场景 | 发现或委派 | 预期帮助 | 用户控制 |
|---|---|---|---|
| 跨材料核对 | 文档中的指标、日期与其他资料可能不一致 | 查找依据，给出引用与修订建议 | 逐条接受或忽略；原件变更可恢复 |
| 报错与卡点 | 页面出现错误或用户直接请求排查 | 解释问题，查资料或项目，提出并验证解决方案 | 代码结果先交付，实际应用变更按权限确认 |
| 内容与信息整理 | 阅读长文、比较选项或直接交办 | 生成摘要、对比、计算和结果文件 | 明确输入范围，不编造未取得的内容 |
| 承诺与跟进 | 任意应用中出现明确的后续事项 | 记录、准备交付、到时提醒 | 可取消；发送与外部提交独立确认 |
| 外部变化连锁处理 | 日程、行程或工作状态变化 | 找出受影响事项，准备调整方案与相关内容 | 跨应用修改、通知和付费行为分开确认 |
| 重复动作接管 | 多次进行相同整理或填写步骤 | 识别模式，提出可复用流程并验证执行 | 先确认范围，再允许指定步骤自动运行 |
| 持续停留 | 在允许的页面停留较久 | 问是否需要解释、整理或下一步帮助 | 可忽略，不据此自动执行 |
| 工作收尾 | 用户主动请求或选择启用定时汇总 | 汇总任务进度、结果和阻塞项 | 只在有内容且需要时出现，不默认制造待办 |

长期目标还包括离开电脑时接收结果、必要时通过其他交互方式拍板。跨设备、语音和外部事件接入属于目标探索，不代表当前原生应用已提供。

## 目标信任与反馈机制

目标动作分级为：只读、生成影子结果、修改原件、对外发送、涉及资金或其他高影响操作。默认可放开的能力应限于明确授权范围；升级操作权限不能仅凭模型自我判断。

目标中的信任积累应可解释：同类动作多次被接受后，可以建议扩大自动化范围，由用户明确确认；被纠正后重新评估范围。当前仅实现显式权限设置，尚无完整的信任评分与自动升降级机制。

规则来源、适用范围和启停状态应可见。每次建议、执行、确认与失败应能追溯；过期信息不得继续推动执行。自主修改原件、恢复和审计完整性仍需进一步建设。

## 核心体验

0. 默认体验由屏幕变化触发：用户继续工作，拾遗主动发现机会；直接委派作为补充入口，二者目标上共用执行能力。
1. 新应用进入前台时询问「看 / 不看」，决定持久保存；设置只展示实际发现的应用，不罗列预设或未安装应用。
2. 允许后读取前台窗口文字，首次建立基线，后续变化交给模型理解。系统和敏感应用排除；用户可闭眼、暂停或撤销。
3. 发现具体帮助机会时说明依据和能做什么，用户可以要求准备结果或规划操作。
4. 直接委派的任务进入后台执行流程，展示当前工具步骤，产出结果文件。缺数据、权限或能力时明确阻塞，允许补充后重试，不用「记下了」冒充执行。
5. 任务与建议统一呈现。已完成任务显示结果与收起入口；阻塞任务显示原因及重试入口。弹窗支持关闭按钮、Esc 和原生外部点击关闭。

## 主动帮助

模型寻找：承诺、跟进、事实核对、时间提醒、报错排查、表单及复杂页面协助、内容整理、流程简化。建议基于页面证据，不把页面中的指令当成授权。

当前实现：变化判断限频约15秒、首次基线不调用判断；建议置信度阈值0.8，默认每小时主动开口预算6次。允许应用连续在前台两分钟可轻量询问一次，同一应用冷却30分钟，有待处理建议时不重复询问。停留按应用计时，不是精确页面计时；重复操作也尚无真实操作序列检测。

## 操作授权

观察与操作独立。三档为只观察、操作前确认、指定控件自动填写。自动模式仅覆盖用户指定名称的文本控件；点击仍需单次确认。执行前复查授权与界面快照，变化则拒绝旧计划。文本填写后重新读取值核对；点击不能仅凭界面变化宣布完成。

## 委派任务

当前执行器通过 Harness 工具循环完成读取、分析、计算与影子目录文件交付，保存计划、结果、状态和验证说明。不再依赖聊天回复分类。任务状态包括 queued、running、completed、blocked、failed；后台中断不自动宣称完成。

当前桌面单步操作规划与委派执行器尚未融合成任意多步操作循环。需要未取得的历史数据、网络或桌面执行的任务，应明确报告阻塞。局部页面快照不能用来统计完整聊天历史。

## 数据与模型

Vision OCR 在本机执行，识别文字发送给模型。轻量模型用于机会判断与操作规划，主模型用于分析及任务执行；通过本机 Harness 调用。材料目录只读，结果写入 shadow/；不得把旧快照说成实时画面。

## 验收现状与限制

- 真实模型：机会判断、单步规划、工具计算及文件交付、建议结果生成读取已分别验证。
- 隔离模拟桥：8项操作权限与结果验证测试通过。
- 真实桌面AX操作：仍被系统辅助功能权限检测拦住，未跑通完整链路。
- 外部点击关闭已编译部署，尚未实测确认。原生更新可能使权限需重新授予。
- Harness定时任务创建不等于提醒已投递桌宠，后者未验证。
- 暂无通用多步桌面任务循环、可靠取消与完整历史采集；不得展示为已具备。

## 后续优先级

稳定应用安装路径与签名、解决原生权限身份；打通真实控件验证；统一主动建议与委派任务执行器；补全排队、取消和恢复；连接定时结果到桌宠；按页面标识完善停留与重复操作判断。

## 独立安装与凭据（v0.3）

项目通过官方 SDK 与固定版本的 npm 运行时依赖启动 Agent，不依赖预安装桌面软件、绝对安装路径或已有登录态。用户 npm ci 后复制 .env.example，填写 SHIYI_API_KEY，运行 npm run check:model 和 npm start。运行时使用独立 SHIYI_HOME/runtime，模型凭据由显式环境变量传入；模型型号可配置，当前供应商固定。源码运行需要 macOS 原生构建环境、Node 24.9+ 和 npm。真实 API 验证需要用户提供 key；模拟测试不能替代该验证。

## 衡量指标与验证方式

| 指标 | 要回答的问题 |
|---|---|
| 主动建议接受率与实际采用率 | 建议是否有价值，而不只是被点击 |
| 忽略、关闭与同类建议重复率 | 是否过度打扰、能否尊重拒绝 |
| 委派任务完成率与阻塞原因 | 真正交付了什么，缺哪些工具或数据 |
| 人工修正率与结果检查通过率 | 结果是否可靠，检查能否发现问题 |
| 完成任务所需的人工时间 | 是否减少了背景解释、监督与收尾负担 |
| 同类反馈重复率 | 规则是否在后续任务中生效 |
| 单任务成本与延迟 | 持续观察和后台执行是否值得 |

当前尚未建立上述指标的完整统计，不能用日志条数、模型置信度或自检声明替代效果数据。应在真实使用样本中对照无助手流程评估。

## 产品价值与风险假设

长期价值在于持续上下文、可执行任务和经确认的工作偏好积累。模型能力提升应扩大可交付范围，产品层负责机会选择、权限与结果体验，而非绑定某一种应用。

主要风险包括观察带来的隐私成本、打扰、错误执行、操作系统权限与界面变化、模型延迟及成本。通过最小观察范围、明确授权、影子产物、可追溯结果与真实验收降低风险；这些仍需验证，不作为已经解决的结论。

## 演示与验收动线

建议用一个跨应用的工作过程展示：发现新应用并授权 → 观察页面变化 → 给出具体建议 → 后台处理并交付依据 → 用户提出修改并确认规则 → 下一项任务应用该规则 → 暂停观察 → 查看任务结果与阻塞原因。

历史「林夏的一天」保留为叙事素材，不要求回到某一个通信应用；原型中的模拟事件必须标注，真实执行与剧本回放分别验收。下一阶段重点验证操作权限、实际控件结果、多步执行与恢复，而非只增加演示场景。

## 待验证与待定

- 停留询问的合适时机与按页面识别方式。
- 哪些具体场景值得常驻观察，哪些适合仅直接委派。
- 多步执行的审批粒度、取消与恢复、原件变更回滚。
- 外部事件、语音与离开电脑后的交互价值。
- 工作偏好的学习范围与可见性，如何避免误学。
- 长期安装、分发、运行成本和目标用户的实际接受程度。
